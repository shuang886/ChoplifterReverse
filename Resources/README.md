# Choplifter Image Assets

I extracted the images from CHOPGFX/HI (now renamed CHOPGFX/HI-reference), and placed them all in this directory. The CHOPGFX/HI files are then regenerated by the `compile-assets.py` script from the Makefile. This means that you can edit the “source” PNGs in this folder and see them change in the rebuilt game.

## Naming Conventions

The first word of the file names are ignored. They’re just for logical grouping.

The rest of the file name will be used in the `sprites.s` tables as a comment. For instance, `Chopper -5 Full tilt forward, nose down.png` will be compiled as:

```
        .word   $a102           ; $a000: -5 Full tilt forward, nose down
```

Images that end in `.pre.png` are special. When compiled, they would be expanded into seven different versions, each shifted one bit to the right. See the section on pre-shifted images for a lot more information.

## Sizing

Modifying the artwork without making them bigger should be fine, but if you make them bigger you should be careful about the binary clobbering something else in memory. Quinn Dunki has identified bits of dead code, so you might delete some of them to make space. Note that the $a102 origin for the bitmaps is assumed in several places (including the loader), so you’ll have to make sure everything matches if you change that.

## Pre-shifted Images

Most of the sprites are straightforward, just 1 bpp monochrome. However, several of them are stored in copies that are each shifted one bit to the right. The asset script will generate this for you, but there are rules.

The PNGs representing these pre-shifted images have one pixel *per bit*, even though each on-screen pixel requires two bits for the six Apple ][ HGR colors. This is because I’m encoding both the palette (high bit that selects green/purple or orange/blue) and the color in the image pixel.

Thus, in general, the PNG will contain two horizontal pixels of the same color for a pixel on the Apple ][ screen. This is so that in the odd case of a two-bit pixel that straddles byte boundaries - and thus can have different palettes (high bits) - the script can know which palette to set for each of the two bits.

In practice, this might happen if a black pixel straddles byte boundaries, where the prior byte is green/purple and the next byte is orange/blue. This invisible quirk appears in `Mountain Mountain 4.pre.png`:

<img width="242" height="86" alt="Screenshot 2025-10-06 at 2 59 02 PM" src="https://github.com/user-attachments/assets/c3c7e84b-c265-40be-a9c9-30fc7b470008" />

where one bit of the fourth pixel-pair from the left in the top row has a different palette as its other bit.

Finally, the script only understands the following colors in the input PNG:

| RRGGBB    | Mapping                |
| --------- | :--------------------- |
| `#000000` | black (high bit unset) |
| `#75fb4c` | green                  |
| `#ea33f7` | purple                 |
| `#d5d5d5` | white (high bit unset) |
| `#646464` | black (high bit set)   |
| `#ec5e2a` | orange                 |
| `#4eacf8` | blue                   |
| `#ffffff` | white (high bit set)   |

Using any other color in the PNG will generate a warning and mangle the output. Note also the Apple ][ feature/quirk that two adjacent 1 bits will turn the pixel white, which the colors above will not account for at all.

So, basically, I barely understand what I just wrote above and you should probably not touch these unless you’re intimately familiar with how Apple ][ HGR colors work. You need to mentally map the color pixels you edit in the PNG to what would show up on screen.
